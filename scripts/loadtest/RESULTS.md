# Korean War 부하 테스트 기록 (k6)

## 측정 환경

- 대상: https://koreanwar-edu.tech (AWS Lightsail $12, 2GB·vCPU 2, 시드니 ap-southeast-2)
  - Docker Compose: Caddy(HTTPS, gzip/zstd) → Next.js standalone → Spring Boot(Java 25, -Xmx512m) → PostgreSQL 18 + PostGIS
- 부하 발생: 사용자 PC(Windows, 한국) 한 대, k6
- 시나리오(`korean-war-load.js`): 가상 사용자 1명이 공개 GET 5개(`/`, `/api/snapshots`, `/api/events`, `/api/stories`, `/api/countries`)를 한꺼번에(batch) 받고 3초 쉬기를 반복. AI 질문·로그인·글쓰기는 부르지 않음
- 합격 기준(thresholds): 전체·주소별 p95 < 1초, 실패율 < 1%
- 주의: 아래 1~5번은 **압축 요청 없이(Accept-Encoding 없음)** 잰 것. 브라우저는 gzip을 요청하므로 실제보다 비관적인 수치다. curl로 보면 gzip 응답이 약 1/3 크기

## 관찰

- 50명에서 캐시 전 db 컨테이너 CPU 100%(docker stats, 눈으로 확인). 원인: 요청마다 같은 공개 자료를 DB에서 다시 읽음
- #92(앱 시작 때 한 번 읽어 메모리에 둠) 뒤 50명: 중앙값 전체 −43%, snapshots −43%, events −30%, stories −49%, 초당 요청 +11%. p95는 거의 그대로(1,855 → 1,755ms)
- 10명(서버 한가)에서도 snapshots 중앙값 1.3초 → 서버 부하가 아니라 **응답 크기 × 한국↔시드니 거리**가 바닥 시간. home(작은 응답) 최솟값 148ms ≈ 왕복 시간
- 반복 한 번에 약 650KB를 받음(압축 없이)

- 6번(gzip, 브라우저와 같은 조건): 받은 양 2.31 → 0.75GB(−68%), 전체 p95 1,755 → 1,365ms, 초당 요청 62.4. 실패 0%
- 6번 동안 서버 CPU(docker stats 5초마다, `stats.csv`, 2 vCPU라 최대 200%):

  | 컨테이너 | 평균 | 최대 |

  | db | 1.6% | 9.8% |
  | backend | 8.1% | 38.0% |
  | caddy | 10.6% | 22.3% |
  | **frontend(Next)** | **60.7%** | **165.5%** |

  → **DB 병목은 해결**(캐시 전 100% → 평균 1.6%). 새 병목은 Next: `/api`·`/photos` 응답을 rewrites로 백엔드에서 받아 다시 넘기는(프록시) 일까지 Next가 한다

## 실험: k6를 Docker 네트워크 안에서 (압축 끔, 2026-11-23 20:44~21:05) — `noencode-docker`

- 바꾼 것 하나: 부하 발생기 위치. Windows k6(PC → Docker Desktop 포트 전달) → k6 컨테이너(Docker 네트워크 안, CPU 2번 한 개). 서버·Caddy 설정·계단은 `noencode-obs`와 같다
- 파일: `result-capacity-noencode-docker.json`, `report-capacity-noencode-docker.html`, `local-stack/stats-capacity-noencode-docker-1123-2043.log`, `run-noencode-docker.meta.txt`

- **결론: 가설이 맞았다.** PC에서 보낼 때의 "한계 300"은 PC → Docker 포트 전달 경로(초당 약 40MB)의 한계였다. 경로를 빼자 같은 서버가 초당 약 **650개**(초당 약 85MB)까지 버텼다. 이번에는 무너질 때 앱 CPU가 거의 다 찼다(서버의 진짜 한계)
- 압축 켬(약 200)과 비교하면, 요청마다 하는 압축이 처리량을 약 1/3로 줄인다 → 다음 실험(미리 압축해 두기)의 근거
- 이상한 구간: 약 9분(20:52:40~20:53:00) 동안 모든 컨테이너가 한꺼번에 약 15~20초 멈췄다(처리량 17요청/초, 중앙값 13.6초, `docker stats` 표본도 19초 빔). 서버가 아니라 PC/WSL 쪽 일시 정지로 보인다. 다시 재서 재현되는지 볼 것. 전체 p95(2.88초)는 이 구간 때문에 커졌다
- 한계 근처에서 k6가 CPU 한 개의 약 70%, 메모리 약 1GB를 썼다. 더 세게 쏠 때는 k6 자원부터 의심할 것
